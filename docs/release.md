# リリース

## バージョンの付け方

バージョンは `vX.Y.Z` の形で、`v0.0.1` から始める。

`v0.Y.Z` の間は、次のように上げる。

| 上げる桁 | いつ | 例 |
| --- | --- | --- |
| Y | 後方互換性を失う変更をしたとき。Z は 0 に戻す | `v0.3.2` → `v0.4.0` |
| Z | それ以外のすべての変更（機能の追加、修正など） | `v0.3.2` → `v0.3.3` |

後方互換性を失う変更の例:

- 起動オプションの削除や意味の変更
- 保存しているファイル（`~/.mybatis-pg/` の接続先・共通パラメータ、ブラウザに保存した個別の値）を、前の版の形のままでは読めなくする変更
- 同じ入力から作られる SQL が変わる変更（不具合の修正を除く）

`v1.0.0` 以降の付け方は、`v1.0.0` を出すときに決める。

## 手順

1. `main` のテストが通っていることを確かめる
2. タグを付けて push する

   ```sh
   git tag -a v0.0.1 -m "v0.0.1"
   git push origin v0.0.1
   ```

3. GitHub Actions の「Release」が動き、テストとビルドの後、GitHub の Releases に次のファイルを添付したリリースを作る
   - `mybatis-pg-0.0.1.jar`
   - `mybatis-pg-0.0.1.jar.sha256`

リリースノートは、前のタグからのコミットと PR から自動で作る。必要なら Releases の画面で書き足す。

## 仕組み

- `pom.xml` のバージョンは `${revision}` で、手元のビルドでは `0.0.1-SNAPSHOT` のようになる。リリースでは、タグから取り出したバージョンを `-Drevision=0.0.1` として渡す
- jar のマニフェストにバージョンを書き込む。`java -jar mybatis-pg.jar --version` で確かめられ、起動時にも表示する
- タグが `vX.Y.Z` の形（先頭の 0 や `-rc` などの付加なし）でなければ、リリースは失敗する
- テストとビルドは `ci.yml` を呼び出して行う（通常の CI と同じ手順）
