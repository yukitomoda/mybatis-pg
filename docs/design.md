# mybatis-pg 設計まとめ

MyBatisのmapper XMLを、パラメータを与えて展開（レンダー）し、PostgreSQLで実行して試すためのツール。名前の「pg」は、playground（試す場所）とPostgreSQLの両方の意味を持つ。XMLの編集はIDEで行い、このツールでは編集しない。

改名前の名前は `mybatis-xml-editor`。改名前の設定（`~/.mybatis-xml-editor/`）とブラウザに保存した内容は、新しい場所になければ起動時に引き継ぐ。

## 目的

MyBatis XMLを直接編集し、構造化したパラメータを与えて、A5M2にそのまま貼れるSQLを得るツールを作る。

- 現状: プレーンSQLを書く → A5M2で試す → MyBatis XMLに手作業で変換する。この変換の手間が大きい
- 狙い: XMLを正として編集し、展開済みSQLをA5M2で確認する流れに置き換える

## 方針

展開はMyBatis本体に任せ、ローカルWebのGUIで操作する。Java型なしで動き、SQL実行はMVPに含めない。

- **展開処理**: MyBatis本体の `XMLMapperBuilder` → `getBoundSql()` をそのまま使い、本番と同じ展開結果を得る。MyBatisは3.4.5に固定し、ビルド時に `-Dmybatis.version` で差し替え可能にする
- **値の埋め込み**（実装済み）: `?` 付きSQLを後から文字列置換すると、文字列・コメント・演算子（`?|` など）中の `?` まで置き換えてしまう。そこで次のようにする
  - `LanguageDriver` を差し替え、SqlSourceは本体に作らせつつ、元の `SqlNode` を保持する
  - `#{}` が残った段階のSQLを取り出し、`#{}` を番号付きの目印に置き換える
  - 目印を `?` に戻したものがMyBatisの `?` 付きSQLと完全一致することを検証してから、目印をリテラルに置き換える
  - 値は `DefaultParameterHandler` と同じ手順で解決する
- **XMLの編集**: IDEで本物のファイルを編集し、ツールは `WatchService` で変更を監視する。`<include>` は別ファイルを参照できるため、変更があれば全mapperを読み込み直す
- **読み込む対象**: 次のどれか1つを起動時に指定する
  - `--project` プロジェクトのディレクトリ（Spring Bootの `mybatis.mapper-locations` から探す）
  - mapper XMLのファイルかディレクトリ
  - `--jar` アプリのJAR（war）。引数に `.jar`・`.war` を渡しても同じ。中（中のJAR、Spring Bootの `BOOT-INF/lib/*.jar` やwarの `WEB-INF/lib/*.jar` を含む）のmapper XMLを一時ディレクトリに取り出して読み込み、画面ではJARの中のパス（中のJARのものは `BOOT-INF/lib/core.jar/mapper/X.xml` のように）で見せる。JARだけを見張り、作り直されたら取り出し直す。編集して試す（下書き）ことはできるが、ファイルには保存できない（プレイグラウンドは使える）。下書き・共通パラメータ・プレイグラウンドはJARのパスでプロジェクトを区別する
- **GUI**: ローカルWeb（JVMサーバ + ブラウザ）
  - ツール自体もJava 8で動かす
  - サーバはJDK標準の `com.sun.net.httpserver` かJavalin 4系。Spring Bootは使わない
  - フロントはReact + Vite。ビルド結果をjarに同梱する（社内ネットワークでCDNが使えない場合に備える）
  - XMLはブラウザで編集しないため、エディタ部品はSQLの表示とJSONの表示に使う程度。軽いCodeMirror 6で足りる見込み
  - 必須のセキュリティ対策: `127.0.0.1` のみにbind、Hostヘッダ検証、起動時トークンの検証、CORS不許可
  - ポート: `--port` を省略すると7171から順に空いているポートを使い、プロジェクトごとなどに複数起動できる。`--port 0` ならOSが選ぶ。リバースプロキシ経由の公開URL（`--public-url`）には `{port}`（code-serverの `{{port}}` も）を書け、使ったポートに置き換える
  - ネイティブ（JavaFX等）やElectron / Tauriは採らない
- **型**: Java型なしで動くことを必須とする
  - パラメータは `Map` / `List` / プリミティブで渡す
  - クラス参照は読み込み前の前処理で取り除く（実装済み。展開結果には影響しない）
    - `resultMap` / `cache` / `cache-ref` 要素を削除
    - statementと `selectKey` の `parameterType` / `resultType` / `resultMap` 属性を削除
    - `parameterMap` の `type` を `map` にし、`parameter` の `javaType` / `typeHandler` を削除
    - SQL本文の `#{}` から `javaType` / `typeHandler` オプションを削除
  - 将来モデルクラスを作ったら、クラスパス指定で本来の型を使えるようにする
- **`databaseId`**: 使っていないため対応しない。`databaseId` 付きのstatementは読み込まれない
- **SQL実行**: MVPの後に追加した（次節）

## SQL実行

画面で接続先を選び、statementをPostgreSQLで実行する。

- **実行方法**: 本番と同じく、MyBatisが作る `?` 付きSQLに、`DefaultParameterHandler`（TypeHandler）で値を設定して実行する。値を埋め込んだSQLは実行しない
- **トランザクション**: 自動コミットを切り、常にトランザクションの中で実行する
  - 既定ではロールバックする
  - 「コミットする」を選んだときだけ、確認のうえコミットする。実行後は既定（ロールバック）に戻す
  - エラーになったら必ずロールバックする
- **接続先**: 名前を付けて複数登録し、画面で切り替える
  - `~/.mybatis-pg/connections.json` に保存する（自分だけが読める権限）
  - パスワードは、既定ではファイルに保存せず、ツールの起動中だけメモリに持つ（再起動したら入力し直す）
  - マスターパスワードを設定すると、選んだ接続先のパスワードを暗号化して `~/.mybatis-pg/secrets.json`（自分だけが読める）に保存できる。鍵はマスターパスワードからPBKDF2（HMAC-SHA256、60万回）で作り、ファイルには保存しない。パスワードは1つずつAES-GCMで暗号化し、接続先のidを認証付きデータにする（別の接続先へ付け替えられないように）
  - 起動するたびに、マスターパスワードを1回入れて開く（接続先の画面、または実行・EXPLAIN・一括チェックの接続先の横）。開くと保存したパスワードを使え、閉じるとメモリから外す。マスターパスワードは変更でき、忘れたら保存したパスワードごと消す
  - ファイルが漏れても、マスターパスワードがなければパスワードは読めない。ツールを動かしているマシンそのものを乗っ取られた場合は守れない
  - JDBCドライバ（pgjdbc）はjarに同梱する
- **結果**: 値はJDBCの `getString` の文字列で表示する（DBの表記のまま）。行数は先頭1000行まで。更新件数と実行時間も表示する
- **実行しないもの**: `<selectKey>`（本体だけを実行し、警告を出す）。`statementType="CALLABLE"` は実行できない

## 共通パラメータ

複数のstatementで同じ値（テナントIDなど）を使うことが多いため、値の集まりを「共通パラメータ」として持ち、statementごとの値（個別の値）と重ねて使う。

- **用語**
  - 共通パラメータ: 複数のstatementで共有する値の集まり。名前を付けて複数作り、場所ごとに適用するかどうかを決める
  - 個別の値: statementごとに入力する値（従来のパラメータ入力）
  - 実際に渡す値: 適用される共通パラメータに個別の値を重ねたもの。レンダリングと実行にはこれを使う
- **重ね方**: パス単位で深く重ねる。個別の値が優先する
  - オブジェクトは項目ごとに重ねる。リスト・文字列・数値・真偽値は丸ごと置き換える
  - 個別の値の「NULL」は上書きとして扱う（共通の値を打ち消せる）。「未設定」なら共通の値を使う
  - statementが参照していない共通の値も渡す（Mapに余分な項目があってもSQLには影響しない）

  ```
  共通（テナントA）:  { tenantId: 100, cond: { status: 1 } }
  個別（search）:     { cond: { name: "taro" } }
  実際に渡す値:       { tenantId: 100, cond: { status: 1, name: "taro" } }
  ```

- **適用**: 共通パラメータごとに「すべての statement に入れる」（既定で入れる）かを決める。statementごと（クエリ画面の「共通」タブ）に、共通パラメータを追加したり外したりできる。既定で入れるものも外せる
- **優先順位**: 適用される共通パラメータが同じ項目を持つときは、順番が下のほうを優先する。順番の既定は共通パラメータの画面の一覧の順で、statementごとにドラッグで並べ替えられる（追加したものは一番下に入る。並べ替えたstatementでは、その順にないものを既定の順番で最後に足す）。個別の値は常に一番優先
- **保存先**: サーバのファイル `~/.mybatis-pg/globals.json` に、プロジェクト（基準ディレクトリの絶対パス）ごとに保存する。共通パラメータの一覧（順番、既定で入れるか、値）と、statementごとの設定（追加したもの、外したもの、並べ替えた順番）を持つ。値はJSONのまま持ち、数値の精度を保つ。個別の値は従来どおりブラウザに保存する
  - 以前の形は、すべて既定で入れるものとし、statementで無効・適用しないにしていたものは、そのstatementで外したものにする。スコープや適用する場所の設定は持たなくなる
- **画面**
  - 画面の上のバーで、「クエリ」「共通パラメータ」「一括チェック」「接続先」の画面を切り替える。画面ごとにURLを分け、切り替えても入力中の内容は消えない
  - 共通パラメータの画面: 左に一覧（ドラッグで既定の順番を並べ替える）、中央に選んだものの「すべての statement に入れる」と値の編集（全statementで使われている項目名を候補として出す）、右にそれを外している（既定で入れないものは追加している）statementの一覧
  - クエリ画面のパラメータ欄: 「個別」と「共通」のタブに分ける。「共通」タブでは、適用する共通パラメータを順番に値とともに並べ、ドラッグで並べ替え、×で外し、「＋ 追加」で追加する（そのstatementだけに効く）。「既定に戻す」で設定を消す
  - 共通から来ている項目には、どの共通パラメータの値かを名前で示し、値を薄く表示する。編集すると個別の上書きになり、上書きした項目には「共通に戻す」ボタンを出す
  - JSON欄は個別の値の表示のままとし、実際に渡す値も確認できるようにする
- **既定の値**: 未設定の項目には、XMLでの使われ方から既定の値を入れる。foreachで回す項目は空のリスト、子の項目を持つ項目は空のオブジェクト（その中にも同様に入れる）。NULLにしたいときは型でNULLを選ぶ
- **既存の機能との関係**: 既定の値は、保存する個別の値ではなく、実際に渡す値を作るときに入れる（共通の値を既定の値で上書きしないため）。「未設定の項目」の表示も実際に渡す値で判定する
- **接続先との連動**: しない。共通パラメータと接続先は別々に選ぶ

## mapper XMLの編集

段階的に、(1) 既存のXMLを編集して実行する、(2) 編集したXMLをファイルに保存する、(3) このアプリだけで使うテンプレート（プレイグラウンド）を作る、へ広げる。いまは (3) まで。

- **編集の単位**: statementを含むmapper XMLファイル全体。クエリ画面の「テンプレート」タブがエディタ（CodeMirror 6）になり、開くと選んだstatementの行へ移る
- **下書き**: 編集した内容は、サーバの `~/.mybatis-pg/drafts/` の下に、プロジェクトごと・ファイルごとに1つのJSONで保存する（読み込み直しても、ブラウザを変えても残る。ブラウザの容量を使わない）。元のファイルは変えない。以前ブラウザに保存していた下書きは、最初に開いたときにサーバへ移す
- **片付け**: 元の内容と同じに戻した下書き、中身が今のファイルと同じになった下書き（外のエディタで同じ変更を保存したなど）は自動で消す。statement一覧の上の「編集中のファイル」に下書きの一覧（更新日時、ファイルがない・変更済みの印）を出し、1つずつ、またはすべてを取り消せる。消えたり名前が変わったりしたファイルの下書きもここで消せる。エディタの「編集を取り消す」でも消せる
- **反映**: 下書きのあるファイルのstatementは、パラメータの木・SQLの組み立て・実行・EXPLAINのすべてで下書きの内容を使う。サーバはそのファイルだけを下書きの内容で読み込み直し（include先のsql断片は他のファイルの読み込み済みのものを使う）、最近の8件を覚えておく
- **エラー**: 下書きを読み込んだときのエラー（XMLの構文エラーなど）は、エディタの該当行に印を付けて一覧にする。statementが下書きにないときもその旨を出す
- **編集中の印**: statement一覧のファイルと「テンプレート」タブに印（●）を付ける
- **ファイルの変更**: 編集を始めた後にファイルが変わったら、その旨を出す（下書きは変更前のファイルをもとにしている）
- **ファイルに保存**: エディタの「ファイルに保存」（エディタの中では Ctrl+S / ⌘S）で、下書きの内容をファイルに書き、下書きを消す。ファイルの変更の見張りで読み込み直される
  - 編集を始めた後にファイルが変わっていたら、上書きしてよいかを確かめる。XMLにエラーがあるときも確かめる
  - 文字コードはXML宣言（`encoding="..."`、なければUTF-8、BOMも見る）に従って読み書きする。下書きの組み立てもその文字コードで読む
  - 元のファイルがCRLFならCRLFで書く（エディタはLFにそろえる）。下書きと元の内容を比べるときは改行の違いを除く
  - 権限や持ち主を変えないよう、置き換えずにその場で書き換える
- **statement一覧**: 下書きのあるファイルは、下書きの中のstatementで一覧を作る（足したものには印（＋）を付けて選べるようにし、消したもの・名前を変えたものも反映する）。下書きにエラーがある間（入力の途中など）は、保存されているファイルのstatementのままにする。下書きを保存するたびに一覧を取り直す
- 一括チェックも、下書きのあるファイルは下書きの内容で調べて実行する

### プレイグラウンド

- このアプリだけで使うmapper XML。プロジェクトのファイルとは別に、`~/.mybatis-pg/playground/` の下にプロジェクトごとに「名前.xml」で置く（中身は普通のmapper XML）。画面では `playground:名前` というパスで扱う
- 単位はmapperファイルの形（1つに `<mapper>` が1つ。statementや `<sql>` をいくつでも書ける）。作ると `namespace="playground.名前"` のひな形から始まる
- statement一覧のいちばん上に「プレイグラウンド」の欄を置き、「＋」で作る。読み込めないものには⚠を付ける。statementがない・読み込めないものも一覧に出し、鉛筆でエディタを開ける
- 下書きは使わず、編集したら自動で保存する（Ctrl+S ですぐに保存）。名前の変更・削除はエディタの上のボタンで行う
- プロジェクトのmapper XMLの `<sql>` を include できる（下書きと同じ仕組みで、プレイグラウンドだけを読み込み直す）。プロジェクトと同じidのstatementは、プロジェクトのものを使う
- パラメータ・共通パラメータ・SQL・実行・EXPLAIN・一括チェックは、プロジェクトのstatementと同じように使える

## サブクエリの分析（部分ごとに実行）

サブクエリが多いSQLで、どの部分が何を返しているかを調べるための機能。結果の列の「サブクエリ」タブに置く（statementを1回実行する実行タブとは用途が違うため、タブを分ける）。サブクエリ・CTEがなければ、その旨だけを出す。

- **見つけ方**: 構文を完全には解析せず、文字列・コメント・引用（ドル記号の引用、入れ子のコメントを含む）を読み飛ばしながら括弧の対応を取り、`SELECT`・`WITH`・`VALUES` で始まる括弧をサブクエリとして拾う（PostgreSQL特有の書き方があっても壊れにくくするため）。種類はCTE、FROMの中、IN・ANYなどの条件、EXISTS、SELECTの列、式の中
- **木**: 部分を木で見せ、選ぶとSQLの中の位置を色付けする。「すべての部分を実行」で、外側の値がいらない部分の件数をまとめて出す
- **実行**: 部分は、バインド変数を `$1, $2, ...` にしたSQLから切り出し、サーバでその部分が使う番号のバインド変数だけを本番と同じ手順（`DefaultParameterHandler`。foreachの要素の変数も引き継ぐ）で渡して実行する。全体の実行と件数がそろう
  - CTEやメインの本体のサブクエリは、見えるCTE（データを書き換えるものは除く）を前に付けて実行する。再帰のCTEにも対応する
  - 読み取り専用のトランザクションで実行し、必ずロールバックする。`SELECT * FROM (...)` で包むため、`;` で区切った別の文は構文エラーになる。行は上限まで返し、超えたら全体の件数を数える
  - データを書き換える部分（DELETEなどのメインのクエリ、`WITH x AS (DELETE ...)`）は実行しない
- **相関サブクエリ**: 部分の中で定義されていない別名で修飾した参照（`o.id` など）のうち、外側で定義された名前のものを外側への参照とし、「相関」の印を付ける。外側の値は、パラメータ欄と同じ入力（型の選択、ƒ での式の挿入とプレビュー、未設定の警告）で入れる。値は式を計算したうえで、型に合わせたSQLの書き方（文字列は `'...'`、日時は `TIMESTAMP '...'`、日付は `DATE '...'`、PGの型は `CAST('...' AS 型)` など）にして埋め込んで実行する。入れた値はstatementごとにブラウザに覚えておく
- **限界**: 別名を付けずに外側の列を参照する相関は見分けられない（単独で実行したときのエラーで気づく）。MyBatisが展開した後のSQLを見るため、foreachで同じ形のサブクエリが並ぶと見分けにくく、XMLのどこから来たかは分からない
- **今後の案**: 外側の結果から1行を選ぶと値が入る、条件の内訳（外側の行ごとに各サブクエリの条件の真偽を並べる）、EXPLAINのサブクエリごとの実行回数・行数を木に重ねる

## EXPLAIN

クエリの性能の問題を調べるため、statementの実行計画を取得して表示する。対象はPostgreSQL 11以降。

- **取得**: 結果の列の「EXPLAIN」タブで、今のパラメータのまま `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` を実行する。SQLとバインド値は実行と同じく本番と同じもの（`?` とTypeHandler）を使う
  - ANALYZEではSQLを実際に実行するが、トランザクションは必ずロールバックする。ANALYZEなし（計画のみ）も選べる
  - BUFFERSはANALYZEと一緒でないと使えない（PostgreSQL 11）
  - 読み取り専用のトランザクション（更新系はエラー）と、タイムアウトを選べる
- **貼り付け**: 本番などで取ったEXPLAINの結果（テキスト形式またはFORMAT JSON）を貼り付けて、同じ表示で見られる。検証環境はデータ量が本番と違い、計画が変わることがあるため、比べる相手として使う
- **表示**: 計画をツリーの表で表示する。列は、ノード自身の時間（全体に占める割合を棒で示す）、合計の時間、行数（実績 / 見積もり）、ループ数、バッファ（キャッシュ / ディスク）
  - ノード自身の時間は、合計の時間から子のノードの時間を引いたもの。Gatherの下（並列実行の部分）はプロセスの数で割って経過時間の目安にする
  - 実績と見積もりの行数が10倍以上ずれているノード、ディスクからの読み込み、一時ファイルの使用に印を付ける
  - ノードをクリックすると、条件やSort Methodなどの詳細を表示する
- **自動の指摘**: 計画から、よくある原因を日本語で指摘する。根拠（計画から読み取った値）と、確かめること・対処の候補を出し、断定はしない。対象のノードには印を付ける
  - 時間の多くを占めるノード（自身の時間が全体の40%以上）
  - 見積もりと実績の行数のずれ（10倍以上）。Limitの下で実績が少ないのは、途中で読むのをやめるためなので指摘しない
  - 全件読み込みで大半（90%以上、1000行以上）を条件で捨てている。インデックスで読んで大半を捨てている
  - 並べ替えがディスクを使っている（external）、ハッシュの分割（Batches が2以上）、ビットマップの lossy
  - 入れ子ループの内側を1000回以上実行している（内側が全件読み込みなら強く指摘）
  - ディスクからの読み込みが多い（キャッシュに乗っていない可能性）
- **6回目の計画（汎用プランの確認）**: JDBCは同じSQLを6回目以降、サーバ側で準備した文として実行し、サーバは値に依らない計画（汎用プラン）を使うことがある。PostgreSQL 11には汎用プランを直接見る方法（12以降の plan_cache_mode、16以降の GENERIC_PLAN）がないため、同じ状況を再現する
  - `PREPARE` し、`EXPLAIN EXECUTE` で計画だけを5回作ってから（実行しない）、6回目を EXPLAIN する。更新系のSQLでも5回実行されることはない
  - PREPAREのパラメータの型は、JDBCが送る型に合わせる（文字列は varchar、接続パラメータが stringtype=unspecified なら unknown。整数は int8 など）。値は型を決めないリテラルで渡す
  - 計画の条件に `$1` などが残っていれば汎用プランと判定し、その旨を表示する
- **比較**: 表示している結果を「比較用に残す」で名前を付けて残し（statementごとにブラウザへ、20件まで）、選んだ2件以上を並べて比べる。パラメータや共通パラメータを変えた比較も、XMLの修正やインデックスの追加の前後の比較も、同じ仕組みで行う
  - 実行時間、計画時間、コスト、読んだブロック（キャッシュ / ディスク / 一時ファイル）、結果の行数を並べ、左端に対する倍率を出す
  - 汎用プランかどうか、時間のかかったノード、表の読み方、指摘の数、パラメータも並べる。下に各計画のツリーを横に並べる
- **繰り返し**: ANALYZEを指定した回数（20回まで）繰り返し、最小・中央値・最大の実行時間を出す。毎回別のトランザクションで実行してロールバックする（更新系でも重複などのエラーにならない）。表示する計画は中央値の回のもの
- **表の情報**: 計画に出てくる表について、行数（統計）、サイズ、不要な行の数、統計を最後に更新した日時、全件読み込みとインデックスで読まれた回数、インデックスの一覧（定義、サイズ、使用回数）を出す。読み取り専用のトランザクションで読む
  - 統計の更新が30日以上前（または一度もない）、不要な行が生きている行の20%を超える、使われていないインデックス、に印を付ける
  - DBから取った計画では自動で読み、貼り付けた計画では押したときだけ読む（どのDBの計画か分からないため）
- **一括チェック**: statement一覧の上の「一括チェック」から、statementをまとめてEXPLAINし、コスト・見積もりの行数・実行時間・全件読み込みする表・指摘の数を一覧にする（並べ替えられる。行を押すとそのstatementのEXPLAINタブを開く）
  - 値は画面で開いたときと同じく、ブラウザに保存した個別の値・共通パラメータ・既定の値・式から作る
  - 既定は計画のみ（実行しない）。ANALYZEを選んだときも、実行するのはSELECTだけで、読み取り専用のトランザクションで実行する（更新系は計画のみ）
  - statementの種類（SELECT・INSERTなど）は /api/statements で返す

## 生成値（式）

値を直接書く代わりに、計算や自動生成した値を使えるようにする（日時のUNIX時刻への変換、現在時刻、UUIDなど）。

- **書き方**: 文字列と数値の入力欄に `{{関数:引数1|引数2}}` の形の式を書く。文字列では他の文字と組み合わせられる（`user-{{uuid}}`）。数値の欄では、結果が数値になる式だけを使える。`{{` を文字として使うときは `\{{` と書く
- **入力の補助**: 入力欄の横の「ƒ」ボタンで、関数を選んで引数を入れるパネルを開く。結果のプレビューを見て「挿入」を押すと、カーソルの位置に式が入る
- **関数**

  | 式 | 結果 | 例 |
  | --- | --- | --- |
  | `{{uuid}}` | 文字列 | UUIDv4 |
  | `{{date:基準\|書式}}` | 文字列 | `{{date:now-7d\|yyyy-MM-dd}}` → `'2026-10-08'`。書式の既定は `yyyy-MM-dd HH:mm:ss` |
  | `{{unixtime:基準\|単位}}` | 数値 | `{{unixtime:2026-01-03 23:35}}` → `1767450900`。単位は `s`（既定）か `ms` |
  | `{{random:最小..最大}}` | 数値 | 範囲内の整数 |
  | `{{randstr:長さ}}` | 文字列 | 英数字。長さの既定は16 |

  - 基準: `2026-01-03`、`2026-01-03 23:35`、`2026-01-03 23:35:10` などの日時（末尾に `+09:00` や `Z` も付けられる）、または `now` / `today`。どちらにも `-7d` `+1M` のような相対指定（単位 `y` `M` `d` `h` `m` `s`）を続けられる。省略すると `now`
  - 書式: `yyyy` `yy` `MM` `M` `dd` `d` `HH` `H` `mm` `m` `ss` `s` `SSS` の組み合わせ（Javaと同じ）。`'` で囲んだ部分はそのまま出す
- **作り直すタイミング**: 一度計算した値は固定し、表示・コピー・実行で同じ値を使う。式を書き換えるか、行の「↻」を押すと作り直す。ページを開き直しても作り直す
- **タイムゾーン**: ブラウザのタイムゾーンで解釈・表示する。式の中にオフセットを書いたときはそれに従う
- **計算する場所**: ブラウザで計算し、サーバには計算後の値を送る。保存するのは式のまま（個別の値・共通パラメータとも）
- **表示**: 式のある入力欄の下に結果を出す。SQLタブには使った式と結果の一覧を出す。式の誤りや、数値の欄で結果が数値にならないときは、行を赤くして理由を出し、レンダリングと実行を止める

## パラメータ入力UI

入力はJSONを直接書く形にしない。JSONは、構造化した値をMyBatisに渡すための内部形式と保存形式として使う。

画面はツリー形式とし、statementのXMLから抜き出した項目を最初から並べておく。

```
(パラメータ)                               [＋項目]
  ├ cond          [オブジェクト ▼]          [＋項目] [×]
  │   ├ name      [文字列 ▼] [taro      ]            [×]
  │   └ status    [NULL   ▼]                        [×]
  ├ ids           [リスト ▼]                [＋要素] [×]
  │   ├ [0]       [数値 ▼]   [1         ]            [×]
  │   └ [1]       [数値 ▼]   [2         ]            [×]
  ├ deleted       [真偽値 ▼] [☐]                    [×]
  └ orderBy       [文字列 ▼] [id DESC   ]            [×]   ※ ${} なのでSQLにそのまま埋め込まれる
```

- **項目の抽出元**: `#{...}`、`${...}`、`<if test>` / `<when test>` の式、`<foreach collection>`、`<bind value>`
  - 式はMyBatis同梱のOGNLパーサで解析し、`cond.name` のようなプロパティ参照をたどる
  - `<foreach>` の `item` や `<bind>` の名前はローカル変数なので、元の項目に読み替える（例: `users` の各要素の `name`）
- **型の選択**: 文字列・数値・真偽値・NULL・リスト・オブジェクトから選ぶ。リテラルの出力（`1` と `'1'`）や `<if test="status == 1">` の判定が型で変わるため。`jdbcType` や式中の比較から推測できる場合は初期値にする
- **手での追加**: 解析で拾えなかった項目は「＋項目」で足せる
- **参照されていない項目**: XML側で参照されていない項目（打ち間違いや削除済み）はグレー表示などで区別する
- **JSON**: statementごとにJSONで保存する。画面にもJSONを表示し、貼り付けやまとめての書き換えに使えるようにする

## MVPの範囲

主な成果物は、値を埋め込んだSQL（A5M2にそのまま貼れるもの）。

1. mapper XMLを読み込み、statement idの一覧を表示する（`application.yml` の `mybatis.mapper-locations` から自動で探せると良い）
2. statementを選び、パラメータを入力する（上記の入力UI）
3. 入力やXMLが変わるたびに再レンダリングし、以下を表示する
   - 値を埋め込んだSQL（コピーボタン付き）。文字列は `''` でエスケープし、数値・`NULL`・真偽値（`TRUE` / `FALSE`）をPostgreSQLの書式で出力する。元の `#{name}` と値の対応を併記する
   - `?` 付きSQLとバインド値の一覧
   - エラー（XMLの構文エラー、OGNLの評価エラー、パラメータの不足）
4. statementごとのパラメータを保存し、次回も使えるようにする

## 既知の制約

- **Map方式でのずれ**: 本番では失敗する書き方が、ツールでは通ってしまう場合がある。将来、mapperインターフェースのシグネチャで検証して補う
  - 単一引数で `@Param` がない場合（本来は `_parameter` で参照する）
  - 単一の `List` 引数の場合（本来は `list` / `collection` で参照する）
- **リテラルとバインドの差**: 暗黙の型変換やインデックスの効き方が稀に変わる
- **日付**: パラメータの型「日時」「日付」で入力すると、本番のアプリ（Javaの日時型）と同じく timestamp・date としてバインドし、値を埋め込んだSQLでは `TIMESTAMP '2026-01-03 23:35:00'`・`DATE '2026-01-03'` と書く。`#{x,jdbcType=TIMESTAMP}`・`jdbcType=DATE` の項目は、最初からこの型にする。文字列のまま入力すると varchar としてバインドされ、`timestamp_col < ?` などが型の不一致でエラーになる（接続パラメータに `stringtype=unspecified` があれば通る）。JSONには日時の型がないため、画面とサーバの間では `{"$type": "timestamp", "value": "..."}` の形で受け渡す
- **整数の型**: JSONの整数は、intの範囲に収まればInteger（int4）、収まらなければLong（int8）としてバインドする。int8のままだと `date + ?` や `substr(s, ?)` が「演算子・関数がない」エラーになるため（本番のIntegerと同じにする）。int8の列と比べてもインデックスは使える
- **TypeHandlerが型を付ける値**: jsonb・uuid・enumなどの列は、本番ではTypeHandlerがPGobjectなどで型を付けてバインドしている。前処理でTypeHandlerを外すため、文字列のままだと `uuid = character varying` のようなエラーになる。パラメータの型「PG の型」で型の名前（jsonb、uuid、public.status、int4[] など）を指定すると、PGobjectにしてその型でバインドし、値を埋め込んだSQLでは `'...'::jsonb` と書く。型の名前はSQLに埋め込むため、英数字と `_`・`.`・`[]` だけを受け付ける（`timestamp with time zone` のような空白を含む名前は `timestamptz` などの別名で書く）
- **typeHandler**: 前処理で取り除くため、本番で値を変換するtypeHandler（例: enumをコード値に変える）を使っていても、入力した値がそのまま埋め込まれる。入力にはDBに入る形の値を書く
- **`lang` 属性**: 別のLanguageDriverを指定したstatementはレンダリングできない。クラスを参照している場合、そのmapperは読み込めない
- **Javaのメソッド呼び出し**: `<if test="@com.example.Util@isEmpty(x)">` のような式は、クラスがないため評価がエラーになる
- **アノテーション**: `@Select` などのアノテーションで書いたSQLは対象外
- **`?` 演算子**: pgjdbcは `#{}` 以外の `?`（`?|` などのjsonb演算子）もパラメータとみなすため、実行がエラーになる（本番でも同じ）。JDBCでは `??` と書く必要があるが、その場合は値を埋め込んだSQLにも `??` が残るため、A5M2では手で直す必要がある
- **`<selectKey>`**: statement一覧に `insert!selectKey` のような別項目として現れる。必要なら画面で隠す
